## 0. 요약

Redis에 새로 들어가는 것은 **캐시 5종 + 스트림 파생 집계 1종 + 토큰 무효화 마커 1종 + 레이트리밋 카운터 2종**이다
(캐시 3종은 2026-08-10 부하 실측 후 확장 — §3-1, 스트림 파생은 같은 날 Kafka 도입 — §3-5).
검토했으나 **넣지 않기로 한 것이 더 많고**, 그 판단 근거가 이 문서의 절반이다.

| 유형 | 대상 | 상태 |
|---|---|---|
| ① 캐시 | 인기상품(카드), 카테고리 트리, 평점, 브랜드명, 상세 정적조각 | 신규 |
| ①ʹ 스트림 파생 | S-1 실시간 방문자(+생존·강등 신호 2종) | 신규 (§3-5) |
| ② 휘발 상태 | 채팅 세션·추천 목록(기존), 토큰 에폭(신규) | 기존 + 수정 3건 |
| ③ 조정 | ShedLock, 세션 발급 SETNX | 기존 유지 (멱등성은 **DB로**) |
| ④ 계수 | 로그인 레이트리밋 | 신규 |

## 1. 원칙

### 1-1. Redis는 "프로세스 밖에 있는 공유 메모리"다

DB가 아니라 메모리다. 여기서 모든 규칙이 나온다.

- 메모리라 **빠르다** → 자주 접근하는 것에 쓴다
- 메모리라 **잃을 수 있다** → 잃어도 되게 설계한 것만 넣는다
- **프로세스 밖**이라 여러 인스턴스가 공유한다 → 공유가 필요한 것에 쓴다

### 1-2. 백엔드에서 Redis 용도는 네 가지뿐이다

새 요구가 오면 **"이거 넷 중 뭐지?"** 부터 묻는다. 넷 다 아니면 대체로 Redis가 답이 아니다(DB나 큐가 맞다).

| 유형 | 답하는 질문 |
|---|---|
| **① 캐시** | 이 계산을 **또** 해야 하나? |
| **② 휘발 상태** | 이 사용자가 **지금** 뭘 하고 있나? |
| **③ 조정** | 서버 여러 대 중 **누가** 할 건가? |
| **④ 계수** | **몇 번** 일어났나? |

### 1-3. 설계의 척추 — 사본이냐 원본이냐

| | 사본 (캐시) | 원본 (세션·락·카운터) |
|---|---|---|
| Redis 죽으면 | 느려질 뿐 → **DB로 우회 (fail-open)** | 기능 불가 → **실패 처리 (fail-fast)** |
| 메모리 차면 | 먼저 버려도 됨 | 버리면 안 됨 |
| 헬스체크 | 포함 금지 | 서비스 의존 시에도 **ALB 타겟에는 미포함** (§4-1) |

**같은 인스턴스에 둘이 섞이면 이 정책들이 충돌한다.** 규모가 커지면 인스턴스를 분리하지만,
지금은 데이터 총량이 작아(§4-2) 축출 자체가 일어나지 않으므로 `volatile-ttl` 정책 + 축출 알람으로 대신한다.

### 1-4. 키를 하나 만들 때마다 답해야 하는 다섯 가지

1. **키 이름** — `[버전:]도메인:용도:식별자`
2. **TTL** — **TTL 없는 키 금지.** 메모리가 새는 유일한 경로다
3. **장애 시 동작** — fail-open / fail-fast 중 무엇인가
4. **원본이냐 사본이냐**
5. **메모리 부족 시 먼저 버려도 되는가**

### 1-5. 안티패턴

| | 왜 |
|---|---|
| DB처럼 영구 저장 | 메모리는 비싸고 사라진다 |
| TTL 없는 키 | 메모리 누수의 유일한 원인 |
| 큰 값(수 MB) | 싱글 스레드라 큰 값 하나가 전체를 멈춘다 |
| `KEYS` 명령 | 전체 스캔 동안 다른 요청이 전부 대기 |
| 트랜잭션 **커밋 전** 캐시 삭제 | 그 찰나에 낡은 값이 되살아난다 |

## 2. 키 지도

```
[기존 — 원본]
chat:session:{sessionId}            채팅 세션 (신원|채널|brandId)        TTL 60분 sliding ← 변경(§2-1)
chat:owner:{타입}:{신원}:{채널}      활성 세션 인덱스                     TTL 세션+1분 (현행 11분) ← 반영(§3-2)
chat:list:{listId}                  추천 목록 (CH-5 조회 전용, 정본은 DB)  TTL 10분 고정
jarvis:*                            ShedLock 스케줄러 락                 락 자체 TTL(50초)

[신규 — 사본]
v1:popular:cards                    인기 상품 카드 완제품 50건            TTL 3분 ← 변경(§3-1, 2026-08-10 구 v1:popular:ids)
v1:category:tree                    카테고리 트리                        TTL 1시간
v1:review:stats:{productId}         평점 count·average                  TTL 1시간 + 리뷰 작성 evict ← 신규(2026-08-10)
v1:brand:names                      전 브랜드 id→이름 맵 (키 1개)         TTL 1시간 ← 신규(2026-08-10)
v1:product:frag:{productId}         상세 정적조각(옵션·이미지·요약)        TTL 1시간 + 판매자 수정·삭제 evict ← 신규(2026-08-10)
p5:home:{memberId}                  P-5 개인화 추천 완제품 (노션 P-5 확정)  TTL 10분 ← 등재 누락 정정(2026-08-10, 아래 ※)

[신규 — 사본 · 스트림 파생 (08 D4·D5, 2026-08-10)]
visitors:{brandId}                  최근 30분 활동 세션 ZSET (S-1 실시간)  TTL 40분 (창+여유)
stream:behavior:connected           브로커 연결 확인 (값 = 연속 시작 시각)   TTL 90초 ← 2026-08-10 개정(구 :alive)
stream:behavior:degraded            발행 실패 마커 (DB 폴백 구간)          TTL 30분 (= 집계 창)

[신규 — 원본]
auth:epoch:{memberId}               토큰 무효화 마커                     TTL 35분
ratelimit:login:ip:{ip}             로그인 시도 (IP 축)                  TTL 10분
ratelimit:login:acct:{email}        로그인 시도 (계정 축)                TTL 10분
ratelimit:upload:member:{memberId}  S-6 업로드 URL 발급 (회원 축)         TTL 창 길이 ← 등재 누락 정정(2026-08-10)
```

※ **`p5:home:`은 `v1:` 프리픽스와 `RedisCache` 공용 진입점의 예외다** — 규칙 위반이 아니라 근거 있는 예외.
① 폴백(비개인화) 응답은 캐시하면 안 되는데(노션 P-5 — 대체분 상관키는 요청마다 발급) `RedisCache.get`은
로더 결과를 무조건 쓰므로 조건부 캐시를 표현할 수 없다. ② 버전 프리픽스가 없어도 역직렬화 실패 시
재계산하는 fail-open이 있어 스키마 변경에 안전하다. 셋째 예외를 만들기 전에 이 사유에 해당하는지 볼 것.

키 앞의 `v1:`은 **캐시 전용 버전 프리픽스**다. 값 스키마가 바뀌거나 잘못된 값을 대량 캐시했을 때
버전만 올려 전체를 버린다(`KEYS`로 훑어 지우는 짓을 안 하기 위해).

### 2-1. TTL은 어디서 나온 숫자인가

시간 축은 서로 물려 있다. 하나를 바꾸면 짝이 되는 값도 봐야 한다.

```
RT 14일 ─(회전)─▶ AT 30분 ─(claim)─▶ 에폭 35분      ※ 에폭 ≥ AT 수명
                     └─(신원 확인)─▶ 티켓 60초 ─(재발급이 밀어줌)─▶ 세션 60분 ─▶ owner 61분
추천 목록 10분  ← 세션이 아니라 자체 근거(§3-2)
```

| 축 | 값 | 근거 |
|---|---|---|
| **채팅 세션** | **60분** sliding | 우리 서비스의 핵심 흐름은 "카드 → 상세 → 리뷰 → 돌아와서 다시 묻기"다. 상품 3~4개를 비교하면 10분을 넘긴다. 60분이면 FE가 대화를 담는 `sessionStorage`(탭 수명)와의 격차도 대부분 사라진다 — "화면엔 대화가 있는데 AI는 잊은" 상태가 짧아진다. 부수 효과로 I-20 발화율이 오른다(05 §245 — TTL이 지난 뒤 로그아웃하면 통지가 아예 없다). ⚠️ **FastAPI 맥락 TTL과 짝**이라 LLM 팀 동조가 필요하고, FastAPI는 인메모리·1대 고정이라 **메모리 여력 확인이 선행**된다 |
| **chat:owner** | **61분** = 세션+1분 | `slide()`가 두 키를 따로 `expire`한다. owner가 먼저 만료되면 다음 CH-1이 새 세션을 발급해 사용자가 맥락 초기화를 겪는다. TTL을 비대칭으로 주면 그 순서가 **구조적으로 불가능**해진다(Lua 불필요) |
| **추천 목록** | **10분 고정** | 세션과 **분리했다**(`app.chat.list-ttl-minutes` — 구 코드는 `sessionTtlMinutes()`를 재사용해서, 세션을 늘리면 이 값이 근거 없이 따라 늘어났다). 값 자체는 유지: 주 방어선이 이미 **CH-5 소유자 검증**(불일치 404)이라 TTL은 심층 방어·메모리 관리 역할이고, 멀티탭에서 `sessionStorage`가 비어 CH-5를 재조회하는 경우가 있어 과하게 줄일 이유가 없다 |
| **AT** | **30분** | 에폭은 "**알았을 때** 끊는 것"이고 AT 수명은 "**모르는 동안**의 상한"이라 **보완재**다(대체재가 아니다). 늘리면 탈취를 모르는 창만 길어지고 얻는 건 재발급 감소뿐인데, 쿠키로 옮기면 사용자가 체감하지 않는다. 줄이면 RT 회전이 잦아져 "동시 갱신 시 한쪽 재로그인" 사고가 늘어난다 |
| **에폭** | **35분** | AT 수명 + 여유. 그 뒤엔 옛 토큰이 전부 만료라 기억할 이유가 없다. ⚠️ **AT 수명과 별개 설정값이라 결합이 코드로 강제되지 않는다** — AT(`jwt` 설정)를 늘리면 `app.auth.epoch-ttl-minutes`도 같이 늘려야 한다. 에폭이 더 짧으면 무효화가 AT 만료 전에 풀린다 |
| **스트림 티켓** | **60초** | 발급 즉시 쓰므로 30초여도 되지만 서버 간 시계 오차 여유가 필요하다. 줄여서 얻는 게 미미하다 |
| **RT** | **14일** | 쇼핑몰 관습(2주~1달) 안. 시연 중 재로그인을 만들지 않을 만큼 길다 |
| **`guest_id`** | **2시간** sliding | 노션 E-1(2026-07-31) 계약값. "로그인과 로그인 사이의 익명 구간"이라는 정의에서 나온 값이라 유지한다 |
| **인기상품 캐시** | **BE 3분 / FE 5분** | 원본이 **7일 누적 집계**라 몇 분 낡음이 순위를 바꾸지 못한다. evict가 없어 TTL이 곧 신선도이므로 **BE ≤ FE** — FE 재조회가 항상 새 값을 받는다(역전되면 FE의 5분 재조회가 헛걸음이 된다). 층별 값을 다르게 둔 건 낡음의 지속 시간으로 어느 층이 물고 있는지 구분하기 위함이기도 하다(2026-08-10) |
| **카테고리 캐시** | **BE 1시간 / FE 30분** | 거의 안 변한다. 런타임 변경 경로가 없어 TTL만으로 관리 |
| **평점·브랜드명 캐시** | **BE 1시간** + 평점만 evict | evict가 신선도를 책임지므로 TTL은 안전망 — 길게 둬도 잃는 게 없다. 낡음이 evict 없는 캐시의 TTL(분 단위)을 넘겨 관측되면 evict 버그라는 신호다(2026-08-10) |
| **레이트리밋 창** | **10분** — 계정 5회 / IP 30회 | 정상 사용자가 10분에 5번 틀릴 일은 드물다. IP는 공유 환경(회사·카페)을 고려해 넉넉히 |

## 3. 유형별 설계

### 3-1. 캐시

**대상 5종** *(2026-08-10 확장 — 부하 테스트에서 RDS CPU 94% 포화 실측, 4대 스케일아웃으로 DB 압력 4배)*

| 키 | 무엇 | TTL | 무효화 |
|---|---|---|---|
| `v1:popular:cards` | 인기 상품 **카드 완제품** 50건 | 3분 | 없음 (TTL에 위임) |
| `v1:category:tree` | 카테고리 트리 | 1시간 | **TTL뿐** — 아래 |
| `v1:review:stats:{productId}` | 평점 count·average | 1시간 | **리뷰 작성 시 evict** (커밋 후) |
| `v1:brand:names` | 전 브랜드 id→이름 맵 | 1시간 | 없음 (변경 경로 없음) |
| `v1:product:frag:{productId}` | 상세 정적조각 — 카테고리·브랜드 요약, 옵션 정체(이름·추가금), 상세 이미지 URL | 1시간 | **판매자 수정·삭제 시 evict** (커밋 후) |

**선정 기준은 "무겁다"가 아니라 "여러 명이 같은 계산을 반복한다"이다.**
인기상품은 ⓐ 개인화가 없어 적중률 100% ⓑ 7일치 주문을 전부 세는 계산이라 인덱스가 좁혀줄 대상이 없다
ⓒ P-5(개인화 추천) 실패 시 트래픽이 여기로 몰리므로 **LLM 장애가 DB 장애로 번지는 것을 막는 격리 장치**다.

**인기상품은 id가 아니라 카드를 통째로 캐시한다** (2026-08-10 전환 — 구 `v1:popular:ids`).
id만 캐시하면 적중해도 하이드레이션(상품·재고·평점·브랜드 4쿼리)이 매 요청 나가 DB 보호가 반쪽이었다.
대가는 카드의 가격·품절이 최대 TTL(3분)만큼 낡는 것 — **홈 카드에는 담기·결제 경로가 없고**(구매는 상세
경유, 상세·주문은 DB 직독) 그쪽이 정합을 보장하므로 수용했다(팀 결정 2026-08-10). P-5 폴백의
sellable() 필터도 이 낡은 purchaseState를 본다(품절 노출 최대 3분, P-5 본체 캐시의 낡음보다 작다).

**평점·브랜드명은 서비스 진입점(`ReviewService.getStats`/`BrandService.getNames`) 안에서 캐시한다** —
호출부(카드 조립 `toCards`·상세·I-1·I-3·I-17)가 전부 무수정으로 수혜를 받는다. 이로써 카드 조립의
DB 왕복은 4 → 2(상품·재고)가 된다. 재고·가격·판매상태는 캐시하지 않는다 — 틀리면 안 되는 축이다.
평점은 상품 단위 키 + `RedisCache.getAll`(MGET 배치, 리뷰 0개 상품도 EMPTY로 캐시 — negative cache),
브랜드는 수십 건뿐이라 전량을 키 하나에 담고 요청 id만 걸러 준다.

**구현 규칙 3가지**

셋 다 `global/cache/RedisCache` 한 곳에 있다. 캐시를 새로 추가할 때 이 규칙을 다시 구현하지 말 것.

1. **트랜잭션 커밋 후 evict** — 커밋 전에 지우면 그 사이 다른 요청이 옛 DB 값을 읽어 캐시를 되살린다.
   `TransactionSynchronization.afterCommit` 콜백 사용(`ReviewService.evictStatsAfterCommit` 참조 —
   동기화가 비활성이면(단위 테스트 등) 경합 자체가 없으므로 즉시 지운다).
2. **스탬피드 방지** — TTL 만료 순간 동시 요청이 같은 무거운 집계를 DB에 때린다.
   SETNX 락을 잡은 하나만 계산하고, 못 잡은 요청은 **짧게 기다렸다 다시 읽는다**.
   그래도 비어 있으면 **직접 계산한다(폴백)** — 락 홀더가 죽었을 때 요청이 멈추면 안 되므로,
   중복 계산 몇 번이 무한 대기보다 낫다. *(순수 TTL 캐시에는 "낡은 값"이 남아있지 않다 —
   만료되면 사라지므로 "나머지는 낡은 값을 반환"은 구현할 대상이 없다.)*
3. **캐시 조회는 fail-open** — 예외를 삼키고 DB로 넘어간다. 역직렬화 실패(값 스키마 변경 등)도
   같은 취급이다. 캐시 장애가 조회 실패가 되면 안 된다.

**evict 지점은 둘이다 — 리뷰 작성(평점), 판매자 수정·삭제(상세 정적조각)**(2026-08-10, 구 "지금은 없다").
둘 다 `RedisCache.evictAfterCommit` 경유 — 커밋 후 실행 규칙이 한 곳에 있다. 카테고리·브랜드는 런타임 변경
경로가 없고(등록·수정 API 없음, 시드로만), 인기상품은 원본이 7일 누적이라 "바뀌는 순간"이 없어
evict 대상이 아니다 — 주문마다 지우면 캐시가 늘 비고, 안 지우면 TTL이 유일한 갱신 수단이므로
**TTL 전용 캐시는 BE ≤ FE**(§2-1). evict가 있는 캐시(평점, 다음 PR의 상세 정적조각)는 반대로
**TTL을 길게** 둔다 — 신선도는 evict가, TTL은 안전망이.

**프론트 캐시 정합 (세트 작업 — 자료실 「FE 캐시 TTL 조정 가이드」 2026-08-10)**
FE가 인기상품·P-5에 30분(SSR revalidate + staleTime)을 잡고 있어 BE 캐시 갱신이 화면까지 오는 길이
막혀 있다. FE를 5분으로 내린다 — **사용자가 보는 낡음의 상한 = FE TTL + BE TTL**(evict 없는 캐시)이고,
evict 있는 캐시는 서버가 FE 캐시를 지워줄 수 없으므로 **FE TTL이 낡음의 보장 하한**이 된다.
순서 의존 없음: FE·BE 어느 쪽이 먼저 배포돼도 무해하다.

### 3-2. 휘발 상태

#### 채팅 세션 (기존) — 수정 4건

| | 수정 | 이유 |
|---|---|---|
| ✅ | **헬스 그룹 분리** (반영됨) | §4-1 |
| ✅ | **CH-7 승계를 멱등으로** (반영됨) | `claimSession`이 `parts[0] != guest`면 403이라 **재시도가 막힌다.** AI 통지(I-23) 성공 후 Redis 갱신이 실패하면 "세션은 회원, owner 인덱스는 게스트"가 고착되고 로그아웃이 그 세션을 못 찾는다. **이미 그 회원 소유면 성공 반환**하면 재시도로 자가 복구된다 |
| ⏸ | **세션 TTL 10분 → 60분** (LLM팀 대기) | 근거는 §2-1. FastAPI 맥락 TTL과 짝인 계약값이라 한쪽만 못 늘린다 |
| ✅ | **owner는 세션+1분** (반영됨 2026-08-10 — 60분 건에서 분리) | 구 설계는 이걸 60분 건에 묶어뒀지만 **LLM 의존이 없는 순수 BE 변경**이다. 두 키의 `expire`가 원자적이지 않아 갱신 도중 죽으면 owner가 먼저 만료 → 세션이 살아 있는데 새 세션 발급(조용한 맥락 초기화). 비대칭이면 그 방향이 구조적으로 불가능하다(반대 방향은 reuseActive가 처리). 현행 10분/11분, 60분 합의 시 61분으로 자동 추종(`ownerTtl()` = 세션+1분) |
| ✅ | **추천 목록 TTL을 세션에서 분리** (반영됨 — `app.chat.list-ttl-minutes`) | 현재 `RecommendationListService`가 `chatProperties.sessionTtlMinutes()`를 재사용한다. 세션을 60분으로 늘리면 **근거가 다른 값이 6배로 따라 늘어난다.** `app.chat.list-ttl-minutes`로 분리하고 10분 유지 |

반대 방향(session만 만료)은 `reuseActive` empty → `create()` → SETNX 실패 → 강제 덮어쓰기 경로가 이미 처리하고,
죽은 세션을 가리키는 owner로 인한 I-20 중복 통지는 멱등이라 무해하다.

**고치지 않는 것**: 고아 세션 키(TTL로 소멸, SETNX 실패 경로는 이미 정리), 세션 값 문자열 파싱
(`subType|sub|channel|brandId` — 값이 숫자·UUID·enum이라 현재 안전. 필드를 더 넣게 되면 그때 JSON으로).

**감수하는 것**: 탭 수명(무한)과 세션 TTL의 불일치. 시간을 늘려도 경계만 옮길 뿐 없앨 수는 없다
(60분으로 늘리면 **대부분의 탭 사용 시간을 덮어 실질적으로는 거의 사라진다**).
대신 **조용히 깨지지 않게** — 세션 만료 후 새 sessionId를 받는 시점에 FE가 "이전 맥락 초기화"를 안내한다
(BE 작업 없음, 이미 404 `SESSION_NOT_FOUND`로 신호를 준다).

#### 토큰 에폭 (신규)

`auth:epoch:{memberId}`에 **무효화 시각(epoch 초)** 을 적는다. 검증 시 토큰의 `iat`가 그보다 이르면
거절. 로그아웃·비밀번호 변경·계정 정지·탈취 감지 시 찍으면 **그 사용자의 모든 AT가 즉시 죽는다.**

> **[2026-08-04 변경] 카운터 → 시각.** 구 설계는 "숫자 하나를 증가"였는데 두 가지가 걸렸다.
> ① 발급할 때마다 현재 카운터를 **읽어야** 해서 로그인 경로에 Redis 의존이 생긴다
> ② 키가 TTL로 사라진 뒤 `INCR`하면 1부터 다시 시작해, 더 큰 값을 들고 있던 **기존 토큰이 되살아난다**
> — 무효화가 조용히 풀리는 셈이다. 시각은 둘 다 없고, 토큰이 이미 들고 있는 **표준 `iat`를 그대로 써서
> 새 claim도 발급 시 조회도 필요 없다.**

- TTL은 AT 최대 수명보다 길기만 하면 된다(35분) — 그 뒤엔 옛 토큰이 전부 만료라 기억할 이유가 없다
- **AT에만 적용.** 스트림 티켓은 수명 60초라 취소가 무의미하고, FastAPI가 Redis를 보면 D7이 깨진다
- **fail-open** — 신원은 토큰 서명으로 확정되므로 "무효화만 잠깐 미적용". 전통 세션이면 없는 선택지다
- **무효 토큰의 401은 `AUTH_TOKEN_EXPIRED`다**(`AUTH_REQUIRED` 아님) — FE가 A-4 재발급을 시도해
  정당한 사용자는 자동 복구되고, RT가 없는 탈취자는 거기서 죽는다. `AUTH_REQUIRED`면 무효화가
  정당한 사용자까지 로그인 화면으로 튕긴다
- 경계는 `<` — 무효화와 **같은 초**에 발급된 토큰은 살린다(로그아웃 직후 재로그인이 초 경계에 걸려
  죽지 않게). `iat`가 초 단위라 1초 미만의 틈이 생기지만, 탈취된 토큰이 무효화와 같은 초에 발급됐을 리 없다
- `iat` 없는 토큰은 통과 → 하위호환. 이미 발급돼 돌아다니는 토큰을 죽이지 않아 **배포 순서 조율이 불필요**
- **현재 트리거는 로그아웃 하나뿐** — 비밀번호 변경·탈퇴·정지 API가 아직 없다(post-MVP 보류).
  생기면 그 자리에서 `TokenEpoch.invalidate()`를 부르면 된다

> **왜 무상태성을 깎으면서까지 하나**: 앱서버 무상태(수평확장에 필요)와 요청 무상태(외부 조회 불필요)는
> 다른 개념이고, 에폭이 깎는 건 후자뿐이다. JWT가 실제로 값을 하는 지점(스트림 티켓)은 무손상이다.

### 3-3. 조정

**기존 유지** — ShedLock(스케줄러 틱당 1대), CH-1 세션 발급 SETNX, I-21 목록 저장 SETNX. 추가 없음.

**멱등성은 Redis가 아니라 DB로 간다.** 주문 중복 방지에 `Idempotency-Key` + **DB 컬럼 + UNIQUE**를 쓴다.
- 이 프로젝트는 돈·재고 영역을 전부 DB 수준에서 방어한다(조건부 UPDATE, 비관적 락). 주문 중복만 휘발성에 맡기면 원칙이 깨진다
- Redis가 죽은 사이 생긴 중복 주문은 **복구가 어려운 사고**다
- 두 번째 요청에 **기존 주문을 찾아 그대로 반환**하는 게 자연스럽다(Redis면 첫 응답을 따로 저장해야 한다)
- ⚠️ ERD 변경이라 **팀 승인 필요**

현재 실태(2026-08-11 정밀화 — "무방비"가 아니라 층이 갈린다): **더블클릭은 FE**(`isPending` 가드)가,
**재결제(O-2) 동시 요청은 DB**(비관적 락 + `isRetryable`)가, **장바구니 경유 순차 재시도는 DB**(행 삭제 →
`CART_ITEM_NOT_FOUND`)가 막는다. 뚫리는 건 두 구멍 — **동시 중복 요청**(두 탭 등)과 **응답 유실 후
재시도**(서버는 성공했는데 실패로 보인 경우). 바로 구매(`items[]`)는 이 두 시나리오에서 어느 층도 안 본다.
피해는 mock 결제라 재고 이중 차감뿐이고 취소(O-4)로 복원 가능 — "복구 어려운 사고"는 아니나,
같은 의도의 주문 두 건은 데이터로 구분 불가라 `Idempotency-Key` 컬럼 없이는 원리적으로 못 막는다.

문서에 누락된 채 구현돼 있었다).

**업로드(`ratelimit:upload:member:`)는 회원 한 축만 센다** — 로그인과 달리 이미 인증을 통과한
판매자라 계정이 곧 책임 주체이고, IP 축은 같은 사무실의 판매자들을 서로 막을 뿐이다. 발급은 S3에
아무것도 만들지 않으므로 막는 대상은 저장 공간이 아니라 **서명 연산과 무제한 업로드 티켓**이다.
아래 판단 기준 ⓑ(정상 사용량 상한이 숫자로 말해진다)를 충족해 레이트리밋이 맞다.
`FixedWindowCounter`(Lua 원자화·fail-open)를 로그인과 공유한다.

- 로그인은 **IP당 + 계정당 두 축을 같이** 센다. IP만이면 분산 공격에 뚫리고, 계정만이면
  공격자가 남의 계정에 실패를 쌓아 잠그는 **DoS**가 된다
- **계정 잠금은 하지 않는다**(DoS 악용) → 5분 등 **일시 차단** 후 자동 해제
- 알고리즘은 **고정 창**(`INCR`+`EXPIRE`)으로 충분 — 목적이 정밀 과금이 아니라 남용 차단.
  두 명령이 갈라져 EXPIRE 누락 시 키가 영구히 남으므로 **Lua로 원자화**
- 응답 `429 RATE_LIMITED` + `Retry-After` — FastAPI가 이미 같은 코드를 쓰므로 어휘를 맞춘다
- **fail-open** — 못 세면 통과. "잠깐 방어 없음" < "전원 로그인 불가"
- ⚠️ nginx 뒤라 `getRemoteAddr()`이 nginx IP다. **`X-Forwarded-For`를 nginx가 덮어쓰는지 확인 필요**

**E-1(`POST /api/events`)은 nginx 몫.** `permitAll`이라 인증이 아니고, 쿠키 없이 부르면 호출마다
`guest` 행이 새로 INSERT되는 **증폭 구조**다. 다만 방어 축이 IP라 앱에 도달하기 전에 막는 쪽이 싸다.

**`/internal`은 레이트리밋 대상이 아니다.** 인증돼서가 아니라 **정상 사용량의 상한이 불명확**하기 때문이다
— 카테고리 잎 43개 반복 호출이 정상 동작이라, 한도를 잘못 잡으면 추천이 중간에 끊긴다.
**방어하려다 기능을 죽이는** 케이스다. 대신 모니터링·알람, 동시 실행 제한/타임아웃, 이상 시 토큰 회전으로 대응한다.

> **판단 기준**: 새 엔드포인트에 레이트리밋을 검토할 때 ⓐ 인증 전인가 ⓑ 정상 사용량의 상한을 숫자로
> 말할 수 있나. ⓑ에 답할 수 없으면 레이트리밋이 아니라 모니터링이 맞다.

### 3-5. 스트림 파생 집계 (2026-08-10 신설 — 08 D4·D5)

`visitors:{brandId}`는 §1-2의 네 유형 중 **① 캐시(사본)**지만, 채우는 방식이 다르다.
cache-aside는 **읽을 때 없으면 만들고**, 이쪽은 **쓸 때 스트림 컨슈머가 계속 갱신한다**(write-through).
그래서 `RedisCache` 진입점을 쓰지 않는다 — 로더가 없기 때문이다.

| | cache-aside (§3-1) | 스트림 파생 (여기) |
|---|---|---|
| 채우는 주체 | 조회 요청 | 컨슈머 B (`visitor-tracker`) |
| 미스일 때 | 로더가 계산 | **폴백 쿼리**(기존 30분 스캔) |
| 신선도 보장 | TTL | 브로커 연결 + 발행 성공 (아래) |

**낡음을 어떻게 아는가** — 이게 이 유형의 유일한 새 문제다. 파이프라인이 멈추면 이 키는 에러가 아니라
**조용히 낡는다.** TTL로는 못 잡는다(멈춰도 키는 살아 있다). 그래서 신호 두 개를 두고 **둘 다** 성립할 때만
값을 믿는다 — `stream:behavior:connected`(컨슈머가 브로커와 실제로 통하고 있음)와
`stream:behavior:degraded`의 부재(발행이 실패하지 않았음). 하나만으로는 부족하다:
컨슈머가 죽어도 발행은 성공하고, 발행이 성공해도 컨슈머가 못 읽고 있을 수 있다.

> ⚠️ **구 설계는 이 키를 "폴링 중"으로 갱신했다 — 틀렸다**(2026-08-10 배포 검증에서 드러남).
> 컨슈머는 브로커가 죽어도 빈 폴을 계속 돌아서, 신호가 브로커 장애 중에도 살아 있었다.
> 이름(`alive`)까지 "스트림 정상"으로 읽혀 **실제 오진을 불렀다.** 지금은 컨슈머 클라이언트 지표
> (`connection-count`·`last-heartbeat-seconds-ago`)를 읽어 판정한다 — 컨슈머 그룹은 원래 브로커에
> 하트비트를 보내므로 합성 이벤트를 만들 필요가 없다.

**값에 "연속 시작 시각"을 담는 이유** — 신호가 *지금* 있다는 것만으로는 부족하다. Redis가 재시작되면
집계 자체가 비는데 신호는 곧 다시 켜져 **빈 집계를 믿게 된다.** 그래서 연속 연결이 집계 창(30분)보다
짧으면 아직 믿지 않는다. Redis 재시작·컨슈머 전면 정지·네트워크 단절이 이 한 규칙으로 함께 걸린다
(롤링 배포는 남은 인스턴스가 갱신하므로 연속성이 끊기지 않는다).

**강등 마커가 30분(= 집계 창)인 이유** — 발행이 회복돼도 장애 구간 이벤트는 스트림에 없다.
그 구멍이 창 밖으로 밀려날 때까지는 DB 폴백이 맞다.

## 4. 인프라

코드는 `REDIS_HOST`/`REDIS_PORT` env만 갈면 되고 변경이 없다. 챙길 것은 설정이다.

### 4-1. 헬스체크 분리 ← 최우선

`/actuator/health`가 ALB 헬스체크 타겟인데, `spring-data-redis`가 클래스패스에 있으면
**Redis 상태가 자동으로 포함**된다. 즉 **Redis 장애 = 인스턴스가 LB에서 빠짐 = 상품 조회·주문까지 전면 중단**이다.
쇼핑은 Redis 없이 되므로 의도는 "채팅만 degrade"인데 지금은 성립하지 않는다.

```yaml
management:
  endpoint:
    health:
      group:
        liveness:            # ALB가 보는 것
          include: db
        readiness:           # 운영자가 보는 것
          include: db, redis
```

**캐시·세션 양쪽에서 나온 공통 결론이며, 캐시 도입과 무관하게 지금도 유효한 개선이다.**

⚠️ **`SecurityConfig`의 permitAll을 `/actuator/health/**`까지 열어야 한다.** 정확 경로(`/actuator/health`)만
열려 있으면 그룹 엔드포인트가 **401**을 돌려주고, ALB는 그걸 죽은 인스턴스로 읽어 전부 빼버린다 —
분리하려다 더 큰 장애를 만든다. `show-details` 기본값이 `never`라 컴포넌트 상세는 노출되지 않는다.

**검증 방법**: Redis를 내린 상태에서 두 엔드포인트가 갈려야 한다 —
`/actuator/health/liveness` = `UP`(200), 집계 `/actuator/health` = `DOWN`(503).
전자는 트래픽 라우팅용이고 후자는 운영자가 Redis 문제를 보는 창이다.

### 4-2. 메모리 정책

권고는 `volatile-ttl`(남은 TTL 짧은 순 축출 — 수명 짧은 캐시·레이트리밋이 세션보다 먼저 나감)이었으나,
**실배포는 `volatile-lru` 유지로 수용됐다**(2026-08-04 배포 담당 — 사용률 1.6%라 축출 자체가 안 일어나고,
정책 변경은 클러스터 재생성이 필요). 아래 결론("보험이지 설계 제약이 아니다")이 그 수용의 근거다.

**이 정책은 보험이지 설계 제약이 아니다.** 실사용량을 계산하면 축출이 일어날 일이 없다(2026-08-10 갱신):

| | 크기 |
|---|---|
| 세션 | 동시 1만 명 × ~100B = **1MB** |
| 캐시 | 인기 카드 50건 ~30KB + 평점·조각 상품당 ~10KB × 300 + P-5 회원별 ~5KB = **수 MB** |
| 레이트리밋 | 활성 IP·계정·회원 × ~50B = **수백 KB** |
| **합계** | **10MB 미만** — 실노드 384MB(ElastiCache t3.micro)의 3% 이하 |

그러므로 **"캐시 TTL을 세션보다 짧게" 같은 규칙으로 TTL을 깎지 않는다.** TTL은 §2-1의 자체 근거로 정하고,
축출은 **`Evictions > 0` 알람**으로 감지해 그때 대응한다. 일어나지 않을 일을 위해 캐시 효과를 미리 버릴 이유가 없다.

### 4-3. ElastiCache 전환 시 (형상 확인 후)

- JVM `-Dnetworkaddress.cache.ttl=30` — failover 후 옛 IP로 계속 붙는 것 방지(AWS 권장)
- ~~TLS(`spring.data.redis.ssl.enabled`) + AUTH 토큰~~ — **이번 프로젝트 기간 미적용 확정**(2026-08-04 배포 담당).
  켜려면 클러스터 재생성이 필요하고, 보안그룹으로 VPC 내부에서만 열려 있어 잔여 기간 위험이 낮다는 판단이다.
  현재 배포는 평문·무인증으로 동작한다 — **수용된 위험**이지 누락이 아니다
- **replica 읽기 분산은 하지 않는다** — 방금 쓴 값이 안 보이는 문제(무효화 직후 특히 위험)
- CloudWatch 알람: `Evictions > 0`, 메모리 사용률, `CurrConnections`

~~⚠️ 선행 확인: `REDIS_HOST`가 ElastiCache인지 컨테이너인지~~ — **해소(2026-08-04 배포 담당 회신):
ElastiCache `cache.t3.micro` 단일 노드·복제본 0.** 배포해도 채팅이 안 끊긴다. 단일 노드라 AWS 유지관리
재시작 시 Redis가 비는데, 그건 "대화 맥락 초기화"지 로그아웃이 아니다(인증은 JWT+MariaDB RT) — 수용.
남은 확인: JVM `-Dnetworkaddress.cache.ttl=30` 실적용 여부(위 첫 항목 — 유지관리 노드 교체 시 IP가
바뀌면 JVM 기본 DNS 캐시가 옛 IP를 물고 전 인스턴스의 Redis 연결이 동시에 죽는다), 유지관리 창이
발표(8/14)와 겹치는지.

## 5. 넣지 않기로 한 것

| 흔한 Redis 용도 | 우리는 |
|---|---|
| 재고 예약 | 조건부 UPDATE + 보상 복원으로 이미 해결. 얹으면 재고 진실이 둘이 된다 |
| 장바구니 동시성 | `PESSIMISTIC_WRITE`로 해결 |
| 중복 이벤트 제거 | `behavior_events.client_event_id` UNIQUE로 DB가 처리 |
| 캐시 무효화 Pub/Sub | 캐시가 Redis에 있으니 지우면 전 서버에 즉시 반영 |
| SSE 팬아웃 | 채팅은 FE↔FastAPI 직결(D5)이라 BE와 무관 |
| 실시간 랭킹(ZSET) | 인기상품은 5분 캐시로 충분. 실시간일 이유가 없다 |
| 조회수 카운터 | `behavior_events` 원본이 분석에 필요해 DB 유지 |
| 이메일 인증·비번 재설정 토큰 | **그 기능이 없다** |
| 주문 멱등성 키 | **DB로** (§3-3) |
