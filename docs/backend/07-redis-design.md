## 0. 요약

Redis에 새로 들어가는 것은 **캐시 2종 + 토큰 무효화 마커 1종 + 레이트리밋 카운터 2종**뿐이다.
검토했으나 **넣지 않기로 한 것이 더 많고**, 그 판단 근거가 이 문서의 절반이다.

| 유형 | 대상 | 상태 |
|---|---|---|
| ① 캐시 | 인기상품, 카테고리 트리 | 신규 |
| ② 휘발 상태 | 채팅 세션·추천 목록(기존), 토큰 에폭(신규) | 기존 + 수정 3건 |
| ③ 조정 | ShedLock, 세션 발급 SETNX | 기존 유지 (멱등성은 **DB로**) |
| ④ 계수 | 로그인 레이트리밋 | 신규 |

## 1. 원칙

### 1-1. Redis는 "프로세스 밖에 있는 공유 메모리"다

DB가 아니라 메모리다. 여기서 모든 규칙이 나온다.

- 메모리라 **빠르다** → 자주 접근하는 것에 쓴다
- 메모리라 **잃을 수 있다** → 잃어도 되게 설계한 것만 넣는다
- **프로세스 밖**이라 여러 인스턴스가 공유한다 → 공유가 필요한 것에 쓴다

### 1-2. 백엔드에서 Redis 용도는 네 가지뿐이다

새 요구가 오면 **"이거 넷 중 뭐지?"** 부터 묻는다. 넷 다 아니면 대체로 Redis가 답이 아니다(DB나 큐가 맞다).

| 유형 | 답하는 질문 |
|---|---|
| **① 캐시** | 이 계산을 **또** 해야 하나? |
| **② 휘발 상태** | 이 사용자가 **지금** 뭘 하고 있나? |
| **③ 조정** | 서버 여러 대 중 **누가** 할 건가? |
| **④ 계수** | **몇 번** 일어났나? |

### 1-3. 설계의 척추 — 사본이냐 원본이냐

| | 사본 (캐시) | 원본 (세션·락·카운터) |
|---|---|---|
| Redis 죽으면 | 느려질 뿐 → **DB로 우회 (fail-open)** | 기능 불가 → **실패 처리 (fail-fast)** |
| 메모리 차면 | 먼저 버려도 됨 | 버리면 안 됨 |
| 헬스체크 | 포함 금지 | 서비스 의존 시에도 **ALB 타겟에는 미포함** (§4-1) |

**같은 인스턴스에 둘이 섞이면 이 정책들이 충돌한다.** 규모가 커지면 인스턴스를 분리하지만,
지금은 **"캐시 TTL < 세션 TTL"** 규칙 + `volatile-ttl` 정책으로 대신한다(§4-2).

### 1-4. 키를 하나 만들 때마다 답해야 하는 다섯 가지

1. **키 이름** — `[버전:]도메인:용도:식별자`
2. **TTL** — **TTL 없는 키 금지.** 메모리가 새는 유일한 경로다
3. **장애 시 동작** — fail-open / fail-fast 중 무엇인가
4. **원본이냐 사본이냐**
5. **메모리 부족 시 먼저 버려도 되는가**

### 1-5. 안티패턴

| | 왜 |
|---|---|
| DB처럼 영구 저장 | 메모리는 비싸고 사라진다 |
| TTL 없는 키 | 메모리 누수의 유일한 원인 |
| 큰 값(수 MB) | 싱글 스레드라 큰 값 하나가 전체를 멈춘다 |
| `KEYS` 명령 | 전체 스캔 동안 다른 요청이 전부 대기 |
| 트랜잭션 **커밋 전** 캐시 삭제 | 그 찰나에 낡은 값이 되살아난다 |

## 2. 키 지도

```
[기존 — 원본]
chat:session:{sessionId}            채팅 세션 (신원|채널|brandId)        TTL 10분 sliding
chat:owner:{타입}:{신원}:{채널}      활성 세션 인덱스                     TTL 11분 ← 수정(§3-2)
chat:list:{listId}                  추천 목록 전달 버퍼                  TTL 10분
jarvis:*                            ShedLock 스케줄러 락                 락 자체 TTL

[신규 — 사본]
v1:popular:ids                      인기 상품 id 목록                    TTL 5분
v1:category:tree                    카테고리 트리                        TTL 1시간

[신규 — 원본]
auth:epoch:{memberId}               토큰 무효화 마커                     TTL = AT 최대 수명
ratelimit:login:ip:{ip}             로그인 시도 (IP 축)                  TTL = 창 길이
ratelimit:login:acct:{email}        로그인 시도 (계정 축)                TTL = 창 길이
```

키 앞의 `v1:`은 **캐시 전용 버전 프리픽스**다. 값 스키마가 바뀌거나 잘못된 값을 대량 캐시했을 때
버전만 올려 전체를 버린다(`KEYS`로 훑어 지우는 짓을 안 하기 위해).

## 3. 유형별 설계

### 3-1. 캐시

**대상은 둘뿐이다.**

| 키 | 무엇 | TTL | 무효화 |
|---|---|---|---|
| `v1:popular:ids` | 인기 상품 id 목록 | 5분 | 없음 (TTL에 위임) |
| `v1:category:tree` | 카테고리 트리 | 1시간 | 카테고리 변경 시 삭제 |

**선정 기준은 "무겁다"가 아니라 "여러 명이 같은 계산을 반복한다"이다.**
인기상품은 ⓐ 개인화가 없어 적중률 100% ⓑ 7일치 주문을 전부 세는 계산이라 인덱스가 좁혀줄 대상이 없다
ⓒ P-5(개인화 추천) 실패 시 트래픽이 여기로 몰리므로 **LLM 장애가 DB 장애로 번지는 것을 막는 격리 장치**다.

**제외 판정과 근거**

| 후보 | 제외 이유 |
|---|---|
| **평점** | `review.idx_review_product`가 이미 있어 12건 집계가 1~3ms. **인덱스는 "적은 행을 콕 집을 때", 캐시는 "많은 행을 통째로 훑을 때"** 효과 — 평점은 전자다 |
| 상품 카드·상세 | PK 조회라 이미 빠르다. 조립 비용의 대부분은 평점 집계였고 그건 위에서 해결 |
| 판매자 지표 | 쿼리는 무겁지만 **반복 조회가 없어 hit율이 안 나온다** + 자기 변경을 즉시 확인해야 하는 화면 |
| 브랜드홈 필터축 | `distinct` 한 방, `brand_id` 인덱스를 탄다 |
| P-5 개인화 추천 | **개인화라 BE 캐시 1벌을 1명이 쓴다** — FE staleTime과 효과가 같다 |
| 장바구니·주문·재고 | 틀리면 돈이 어긋난다. 이미 조건부 UPDATE·비관적 락으로 정확성을 확보한 영역 |
| 검색 결과 | 조건 조합이 매번 달라 재사용이 없다 |

**구현 규칙 3가지**

1. **트랜잭션 커밋 후 evict** — 커밋 전에 지우면 그 사이 다른 요청이 옛 DB 값을 읽어 캐시를 되살린다.
   `@TransactionalEventListener(AFTER_COMMIT)` 사용.
2. **스탬피드 방지** — TTL 만료 순간 동시 요청이 같은 무거운 집계를 DB에 때린다.
   SETNX 뮤텍스로 **1개만 재계산하고 나머지는 낡은 값을 반환**한다.
3. **캐시 조회는 fail-open** — 예외를 삼키고 DB로 넘어간다. 전역 `timeout: 2s`를 그대로 두면
   Redis 장애 시 모든 조회가 2초씩 까먹으므로, 캐시 경로는 더 짧은 타임아웃을 쓴다.

**프론트 캐시 이관 (세트 작업)**
인기상품 캐시가 지금 프론트에 있다 — `serverApi.ts`의 `revalidate: 30분` + React Query `staleTime` 30분.
BE로 옮기면서 둘 다 제거/축소한다. **캐시는 "값이 언제 틀려지는지 아는 쪽"에 둔다** —
프론트는 품절·숨김을 몰라서 시간이 지나기만 기다려야 한다. 둘 중 하나만 걷어내면 반쪽이 된다.

### 3-2. 휘발 상태

#### 채팅 세션 (기존) — 수정 3건

| | 수정 | 이유 |
|---|---|---|
| 🔴 | **헬스 그룹 분리** | §4-1 |
| 🟡 | **CH-7 승계를 멱등으로** | `claimSession`이 `parts[0] != guest`면 403이라 **재시도가 막힌다.** AI 통지(I-23) 성공 후 Redis 갱신이 실패하면 "세션은 회원, owner 인덱스는 게스트"가 고착되고 로그아웃이 그 세션을 못 찾는다. **이미 그 회원 소유면 성공 반환**하면 재시도로 자가 복구된다 |
| 🟢 | **owner TTL을 session보다 길게** (10분/11분) | `slide()`가 두 키를 따로 `expire`해 "owner만 먼저 만료" → 새 세션 발급 → 사용자가 맥락 초기화를 겪는다. TTL 비대칭이면 그 순서가 **구조적으로 불가능**해진다(Lua 불필요) |

반대 방향(session만 만료)은 `reuseActive` empty → `create()` → SETNX 실패 → 강제 덮어쓰기 경로가 이미 처리하고,
죽은 세션을 가리키는 owner로 인한 I-20 중복 통지는 멱등이라 무해하다.

**고치지 않는 것**: 고아 세션 키(10분 뒤 소멸, SETNX 실패 경로는 이미 정리), 세션 값 문자열 파싱
(`subType|sub|channel|brandId` — 값이 숫자·UUID·enum이라 현재 안전. 필드를 더 넣게 되면 그때 JSON으로).

**감수하는 것**: 탭 수명(무한)과 세션 TTL(10분)의 불일치. 시간을 늘려도 경계만 옮길 뿐이다.
대신 **조용히 깨지지 않게** — 세션 만료 후 새 sessionId를 받는 시점에 FE가 "이전 맥락 초기화"를 안내한다
(BE 작업 없음, 이미 404 `SESSION_NOT_FOUND`로 신호를 준다).

#### 토큰 에폭 (신규)

`auth:epoch:{memberId}` 숫자 하나. AT 발급 시 claim에 담고, 검증 시 토큰 epoch < 현재면 거절.
로그아웃·비밀번호 변경·계정 정지·탈취 감지 시 증가시키면 **그 사용자의 모든 AT가 즉시 죽는다.**

- TTL은 AT 최대 수명이면 충분하다 — 그 뒤엔 옛 토큰이 전부 만료라 기억할 이유가 없다
- **AT에만 적용.** 스트림 티켓은 수명 60초라 취소가 무의미하고, FastAPI가 Redis를 보면 D7이 깨진다
- **fail-open** — 신원은 토큰 서명으로 확정되므로 "무효화만 잠깐 미적용". 전통 세션이면 없는 선택지다
- claim 없는 토큰은 통과시키면 하위호환 → 나중에 얹어도 배포 순서 조율이 불필요

> **왜 무상태성을 깎으면서까지 하나**: 앱서버 무상태(수평확장에 필요)와 요청 무상태(외부 조회 불필요)는
> 다른 개념이고, 에폭이 깎는 건 후자뿐이다. JWT가 실제로 값을 하는 지점(스트림 티켓)은 무손상이다.

### 3-3. 조정

**기존 유지** — ShedLock(스케줄러 틱당 1대), CH-1 세션 발급 SETNX, I-21 목록 저장 SETNX. 추가 없음.

**멱등성은 Redis가 아니라 DB로 간다.** 주문 중복 방지에 `Idempotency-Key` + **DB 컬럼 + UNIQUE**를 쓴다.
- 이 프로젝트는 돈·재고 영역을 전부 DB 수준에서 방어한다(조건부 UPDATE, 비관적 락). 주문 중복만 휘발성에 맡기면 원칙이 깨진다
- Redis가 죽은 사이 생긴 중복 주문은 **복구가 어려운 사고**다
- 두 번째 요청에 **기존 주문을 찾아 그대로 반환**하는 게 자연스럽다(Redis면 첫 응답을 따로 저장해야 한다)
- ⚠️ ERD 변경이라 **팀 승인 필요**

현재 실태: 장바구니 경유는 `deleteAll`이 트랜잭션 맨 끝이라 **순차 재시도만** 막히고 동시 요청엔 뚫린다.
바로 구매(`items[]`)는 완전 무방비.

### 3-4. 계수 — 레이트리밋

**Spring이 맡는 것은 로그인·회원가입뿐이다.**

- 로그인은 **IP당 + 계정당 두 축을 같이** 센다. IP만이면 분산 공격에 뚫리고, 계정만이면
  공격자가 남의 계정에 실패를 쌓아 잠그는 **DoS**가 된다
- **계정 잠금은 하지 않는다**(DoS 악용) → 5분 등 **일시 차단** 후 자동 해제
- 알고리즘은 **고정 창**(`INCR`+`EXPIRE`)으로 충분 — 목적이 정밀 과금이 아니라 남용 차단.
  두 명령이 갈라져 EXPIRE 누락 시 키가 영구히 남으므로 **Lua로 원자화**
- 응답 `429 RATE_LIMITED` + `Retry-After` — FastAPI가 이미 같은 코드를 쓰므로 어휘를 맞춘다
- **fail-open** — 못 세면 통과. "잠깐 방어 없음" < "전원 로그인 불가"
- ⚠️ nginx 뒤라 `getRemoteAddr()`이 nginx IP다. **`X-Forwarded-For`를 nginx가 덮어쓰는지 확인 필요**

**E-1(`POST /api/events`)은 nginx 몫.** `permitAll`이라 인증이 아니고, 쿠키 없이 부르면 호출마다
`guest` 행이 새로 INSERT되는 **증폭 구조**다. 다만 방어 축이 IP라 앱에 도달하기 전에 막는 쪽이 싸다.

**`/internal`은 레이트리밋 대상이 아니다.** 인증돼서가 아니라 **정상 사용량의 상한이 불명확**하기 때문이다
— 카테고리 잎 43개 반복 호출이 정상 동작이라, 한도를 잘못 잡으면 추천이 중간에 끊긴다.
**방어하려다 기능을 죽이는** 케이스다. 대신 모니터링·알람, 동시 실행 제한/타임아웃, 이상 시 토큰 회전으로 대응한다.

> **판단 기준**: 새 엔드포인트에 레이트리밋을 검토할 때 ⓐ 인증 전인가 ⓑ 정상 사용량의 상한을 숫자로
> 말할 수 있나. ⓑ에 답할 수 없으면 레이트리밋이 아니라 모니터링이 맞다.

## 4. 인프라

코드는 `REDIS_HOST`/`REDIS_PORT` env만 갈면 되고 변경이 없다. 챙길 것은 설정이다.

### 4-1. 헬스체크 분리 ← 최우선

`/actuator/health`가 ALB 헬스체크 타겟인데, `spring-data-redis`가 클래스패스에 있으면
**Redis 상태가 자동으로 포함**된다. 즉 **Redis 장애 = 인스턴스가 LB에서 빠짐 = 상품 조회·주문까지 전면 중단**이다.
쇼핑은 Redis 없이 되므로 의도는 "채팅만 degrade"인데 지금은 성립하지 않는다.

```yaml
management:
  endpoint:
    health:
      group:
        liveness:            # ALB가 보는 것
          include: db
        readiness:           # 운영자가 보는 것
          include: db, redis
```

**캐시·세션 양쪽에서 나온 공통 결론이며, 캐시 도입과 무관하게 지금도 유효한 개선이다.**

### 4-2. 메모리 정책

`maxmemory-policy=volatile-ttl`. **`volatile-lru`로는 세션이 보호되지 않는다** — 우리 키가 전부 TTL을 갖기 때문이다.
`volatile-ttl`은 남은 TTL이 짧은 것부터 버리므로, **캐시 TTL(5분) < 세션 TTL(10분)** 규칙만 지키면
캐시가 먼저 축출되고 세션이 살아남는다.

### 4-3. ElastiCache 전환 시 (형상 확인 후)

- JVM `-Dnetworkaddress.cache.ttl=30` — failover 후 옛 IP로 계속 붙는 것 방지(AWS 권장)
- TLS(`spring.data.redis.ssl.enabled`) + AUTH 토큰 — 전송 암호화를 켜면 필수.
  **현재 배포는 평문·무인증**이다(설정에 ssl/password 없음)
- **replica 읽기 분산은 하지 않는다** — 방금 쓴 값이 안 보이는 문제(무효화 직후 특히 위험)
- CloudWatch 알람: `Evictions > 0`, 메모리 사용률, `CurrConnections`

⚠️ **선행 확인**: `REDIS_HOST`가 ElastiCache 엔드포인트인지 EC2 컨테이너인지 문서로 판별되지 않는다.
DEPLOY.md는 형상 A(dev 1대)를 기본으로 하고 ElastiCache는 형상 B로만 언급한다.
컨테이너라면 §4-3 항목은 해당 없고, 대신 **"Redis 재시작 = 진행 중인 모든 대화 증발"**을 감수하는지 정해야 한다.

## 5. 넣지 않기로 한 것

| 흔한 Redis 용도 | 우리는 |
|---|---|
| 재고 예약 | 조건부 UPDATE + 보상 복원으로 이미 해결. 얹으면 재고 진실이 둘이 된다 |
| 장바구니 동시성 | `PESSIMISTIC_WRITE`로 해결 |
| 중복 이벤트 제거 | `behavior_events.client_event_id` UNIQUE로 DB가 처리 |
| 캐시 무효화 Pub/Sub | 캐시가 Redis에 있으니 지우면 전 서버에 즉시 반영 |
| SSE 팬아웃 | 채팅은 FE↔FastAPI 직결(D5)이라 BE와 무관 |
| 실시간 랭킹(ZSET) | 인기상품은 5분 캐시로 충분. 실시간일 이유가 없다 |
| 조회수 카운터 | `behavior_events` 원본이 분석에 필요해 DB 유지 |
| 이메일 인증·비번 재설정 토큰 | **그 기능이 없다** |
| 주문 멱등성 키 | **DB로** (§3-3) |
