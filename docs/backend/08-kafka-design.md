## 0. 요약

Kafka에 태우는 것은 **행동 이벤트 수집 경로(E-1) 하나**다.
검토했으나 **태우지 않기로 한 것이 더 많고**, 그 판단 근거가 이 문서의 절반이다.

```
FE ──HTTP──▶ E-1 엔드포인트 (검증·신원주입·문맥보강 — 기존 그대로)
                 │  produce 성공 → 202 / 실패 → 동기 DB 폴백 후 202 / 둘 다 실패 → 500 (D7)
                 ▼
        Kafka topic: behavior-events  (파티션 3, key = sessionKey)
                 │
    ┌────────────┴──────────────┐
    ▼                           ▼
컨슈머 그룹 A: persister      컨슈머 그룹 B: visitor-tracker
배치 INSERT → behavior_events   상품→브랜드 해석 후
(멱등: client_event_id UNIQUE)  Redis ZSET visitors:{brandId} 갱신
                                → S-1 activeVisitors의 새 원천
```

| 항목 | 결정 | 근거 절 |
|---|---|---|
| 도입 위치 | E-1 수집 경로 + S-1 `activeVisitors` 원천 교체 | §2 |
| 도입하지 않는 곳 | 주문·매출·aiAttribution·I-17·캐시 무효화 | §2-2 |
| 전달 보장 | at-least-once + 컨슈머 멱등 | D3 |
| 브로커 | KRaft 단일 브로커 1대 — 전용 EC2 `jarvis-kafka`(t3.small) | D6 |
| 컨슈머 배치 | 백엔드 앱 내 `@KafkaListener` (4대 분산) — 별도 배포 단위 없음 | D9 |
| 장애 시 | produce 실패 = **동기 DB 폴백 후 202**, 최후에만 500. 컨슈머 장애 = 하트비트 폴백/재개 | D7·D5·§4 |
| 캐시 대안 | 검토 후 비채택 — 빈도 감소 ≠ 작업 소멸, 단 "캐시도 된다"는 인정 | D8 |

## 1. 배경 — 왜 지금, 왜 이 자리인가

- MVP(2026-07-27 종료)는 Kafka 없이 완성했다. 동기 HTTP + DB 집계로 충분한 규모였고, 이는 의도된 선택이다.
- 도전 과제 "Kafka 기반 실시간 데이터 스트림 처리"를 수행하되, **도입을 위한 도입을 피하기 위해
  전 시스템을 후보로 놓고 적합성 판정을 먼저 수행**했다(§2). 탈락 근거를 남기는 것까지가 이 설계의 범위다.
- 부하 테스트(2026-08-08, `부하테스트-병목분석-20260808.md`)로 **"부하·유실 때문에 Kafka가 필요하다"는
  가설은 기각**됐다 — 커넥션 풀 포화 상태에서도 이벤트 유실 0건, 이벤트 경로는 **전체 HTTP 요청 수의 1.2%**
  (1,985 배치 / 168,965 요청 — 요청 수 비율이며 CPU 비중이 아니다).
  따라서 이 설계의 도입 사유에 부하·유실은 **없다**(§1-1 비목표).

### 1-1. 목표 / 비목표

**목표**
1. E-1 수집 경로를 스트림 파이프라인으로 전환 — 같은 이벤트를 저장계(A)와 실시간계(B)가 독립 소비
2. S-1 `today.activeVisitors`(명세: "실시간, 캐시 미적용")를 매 조회 30분 스캔 쿼리 → 라이브 집계로 교체
3. E-1 202 응답의 의미를 "인메모리 큐 수신"에서 "로그 영속"으로 승격 — 노션 E-1의
   "저장 실패 시 500" 문구를 구현이 실제로 이행하게 만든다(§3-3 ①)

**비목표 (명시적으로 아님)**
- ~~유실 방지·부하 흡수~~ — 부하 테스트로 근거 없음이 실측됨. 이 사유를 대외적으로 주장하지 않는다
- ~~주문·매출 스트림화~~ — 돈은 근사 불가, 정본은 `order_item` 집계(02 D32·I-13 개정 원칙)
- ~~I-17 CDC 전환~~ — §2-2
- 다중 브로커·exactly-once — 데모 규모 밖(D6)

## 2. 적합성 판정 — 어디에 넣고, 어디에 안 넣는가

### 2-1. 판정 기준 4문

1. 한 사건을 **서로 다른 관심사의 소비자** 여럿이 각자 소비하는가 (팬아웃)
2. **실시간성** 요구가 명세에 있는가 ("물어볼 때 계산"이면 탈락)
3. **소급 정정 없는 현재-순간 값**인가 (취소 소급·정책 재계산이 있으면 스트림 물질화 부적합)
4. **팀 간 계약 변경 없이** 가능한가 (노션 명세·타 repo 무변경)

### 2-2. 후보별 판정

| 후보 | 판정 | 근거 |
|---|---|---|
| **E-1 + S-1 activeVisitors** | ✅ **채택** | 4문 전부 통과 — 아래 |
| I-17 상품→벡터DB 동기화 | ❌ | CDC의 교과서 자리지만 소비자 1명·분 단위 지연 허용·AI팀 계약 개정 필요. 소비자가 늘면 재평가 1순위 |
| 주문 이벤트 발행 | ❌ | 후속 소비자(알림·정산)가 기획에 없음 — Kafka를 위해 기능을 발명하게 됨 |
| 매출·주문 지표 스트림화 | ❌ | 돈은 근사 불가. 이벤트는 신호, 정본은 DB라는 기존 결정(I-13 purchaseComplete 개정)과 충돌 |
| S-1 aiAttribution | ❌ | 취소 **소급** 반영·귀속 창 재계산·policyVersion 재평가가 요구사항 — "집계 시점 사후 판정"(S-1 명세)이 정답. 스트림 물질화하면 소급이 불가능해짐 |
| 캐시 무효화 (Redis·FE) | ❌ | 늦게 도착한 무효화는 가치 0 — 보존·재생이 전부 낭비. 07 §5의 기존 기각 유지 |
| 판매자 분석(I-6~I-16) 실시간화 | ❌ | 전부 "질의 시점 계산" 요구 — 실시간 감지·알림은 기획에 없음. 채널이 생기면 컨슈머 그룹 추가로 확장(§6) |

**채택 근거 상세** — `activeVisitors`가 유일하게 4문을 전부 통과한다:
- 원천이 `behavior_events`(= 파이프라인에 흐르는 그 데이터)다
- **시점 근거**: 이 지표는 대시보드 화면 확정(2026-07-21, S-1 개정) 때 정의됐다 — **Kafka 검토(2026-08-09)보다
  3주 먼저 존재한 요구**라 "Kafka를 위해 만든 기능"이 아니다. ⚠️ 단, "명세에 실시간이라 적혀 있다"를
  **채택 근거로 쓰지 않는다** — 명세도 우리가 썼으므로 순환논증이다. 명세 인용의 용도는 시점 증명까지이고,
  "왜 스트림이어야 하는가"는 D8(캐시 대안 비교)이 답한다
- 30분 지나면 사라지는 현재-순간 값이라 소급·정정 개념이 없다
- DISTINCT 집계라 **집합 연산으로 자연 멱등** — at-least-once 중복 전달이 숫자를 틀리게 하지 못한다(D3)
- 응답 계약·화면 무변경 — 숫자의 원천만 바뀐다
- **캐시 확장(#147·#148)에서도 살아남은 스캔이다**: 팀은 RDS 부하 대응으로 캐시를 2종→5종으로 늘리면서도
  이 지표는 실시간 성격 때문에 캐시 비대상으로 남겼다(S-1 구현 메모 "activeVisitors만 캐시 미적용" —
  `SellerSalesService.countActiveVisitors` 매 조회 30분 스캔 유지). 캐시 전략이 비켜간 마지막 스캔을 없애는 것이 이 설계다

## 3. 결정 로그

### D1. 토픽은 하나, 키는 sessionKey

- **선택지**: (A) 토픽 1개 `behavior-events` (B) 이벤트 타입별 토픽 분리
- **기준**: 소비자 2개(A·B)가 모두 전 타입을 읽는다. 타입별 분리는 컨슈머 구독만 복잡하게 한다.
- **선택**: (A). 파티션 3 (데모 규모 + 컨슈머 병렬도 여유). 키 = `sessionKey` —
  같은 세션의 이벤트 순서가 보존되고(파티션 내 순서), 세션 수가 많아 핫 파티션이 없다.
  키를 `brandId`로 하면 대형 브랜드 쏠림, 키 없음이면 세션 순서 상실 — 둘 다 기각.
- **트레이드오프**: 파티션 증설 시 같은 세션의 신·구 이벤트가 다른 파티션에 갈라진다(증설은 신중히).

### D2. 프로듀서 — E-1 엔드포인트는 그대로, 적재만 교체

- **선택지**: (A) FE가 직접 브로커/REST Proxy로 발행 (B) E-1 엔드포인트 유지, `@Async` INSERT를 produce로 교체
- **기준**: E-1의 서버 로직(JWT/쿠키 신원 주입, 타입 화이트리스트, 추천 문맥 검증 ③.5, 게스트 쿠키 발급)은
  HTTP 요청 문맥을 요구한다. 브로커 인터넷 노출은 인증·어뷰징 방어를 재발명하게 한다.
- **선택**: (B). 검증·보강 **후**의 완성된 이벤트를 produce한다. 서버 적재 3종
  (`recommendation_generated`·`add_to_cart`·`remove_from_cart`)도 같은 프로듀서를 경유해 적재 경로를 단일화한다.
- **트레이드오프**: produce 동기 대기(acks)만큼 202가 미세하게 늦어진다 — 로컬 브로커라 ms 단위, 감수.

### D3. 전달 보장 — at-least-once + 컨슈머별 멱등

- **기준**: exactly-once는 외부 세계(DB·Redis)를 건드리는 순간 성립하지 않는다. 중복을 전제로 설계한다.
- **선택**:
  - **컨슈머 A**: `client_event_id` UNIQUE(02 D35)가 이미 있다 — 재전달·재처리 모두 DB가 흡수. 기존 배치 INSERT 로직 이식.
  - **컨슈머 B**: `ZADD`는 집합 연산이라 같은 (sessionKey, 시각) 재적용이 결과를 바꾸지 않는다 — 구조적 멱등.
- **트레이드오프**: 없음에 가깝다. 이 자리를 고른 이유 자체가 멱등이 공짜인 자리라서다(§2-2).

### D4. 컨슈머 B — visitor-tracker의 자료구조

- **선택지**: (A) 브랜드별 ZSET `visitors:{brandId}`, member=sessionKey, score=이벤트 시각 (B) HyperLogLog 분 버킷
- **기준**: S-1 정의는 "최근 30분 자사 상품 관련 이벤트의 DISTINCT session_key". 정확한 값 + 슬라이딩 윈도우 + 구현 단순성.
- **선택**: (A). 갱신 = `ZADD`, 조회 = `ZREMRANGEBYSCORE`(30분 밖 제거) + `ZCARD`.
  브랜드 귀속은 컨슈머가 `product_id → brand_id`를 해석(로컬 캐시 가능한 매핑, 스코프 규칙은 S-1과 동일).
  TTL은 키 전체에 40분 — 이벤트가 끊긴 브랜드의 키를 자동 정리.
- **트레이드오프**: 세션 수 × 브랜드 수만큼 메모리를 쓴다 — 동시 1만 세션 기준 수 MB, 07 메모리 정책(§4-2) 안.
  (B) HLL은 메모리는 적지만 근사치라 "정확한 셋"이라는 채택 근거(§2-2)를 스스로 깬다 — 기각.
- **07 키 지도 등재 시 유형**: 사본 계열(폴백으로 재계산 가능 → fail-open, 07 §1-3) · TTL 40분(TTL 없는 키 금지 원칙 준수).
- **집계 대상은 브라우저 세션뿐 (2026-08-10 구현 중 정정)**: 챗봇 경로의 서버 적재 이벤트는
  `session_key`가 `chat:{채팅sessionId}` sentinel이라 **브라우저 세션과 ID 공간이 다르다**(노션 E-1·I-2 한계 ①).
  종전 S-1 쿼리가 이걸 같이 세어 챗봇으로 담은 사람이 자기 브라우저 세션과 별개로 한 번 더 잡혔다 —
  스트림 경로와 **폴백 쿼리 양쪽에서 동시에** 제외한다. 두 경로의 기준이 어긋나면 폴백 전환만으로
  숫자가 튀어 "장애인지 지표 변동인지" 구분할 수 없게 된다.
- **`product_id → brand_id` 해석 = 기동 시 전량 메모리 로드 (2026-08-10 확정, 배포 리뷰 반영)**:
  이벤트마다 DB 조회하면 컨슈머가 커넥션을 상시 소비한다 — 현재 RDS `max_connections` 30에
  앱 4대 × 풀 7 = 28로 **여유가 2뿐**이라 허용 불가. 상품 ~6,300건의 매핑은 수백 KB라
  기동 시 전량 로드 + **주기 리프레시**(5분, 쿼리 1회)로 간다. 리프레시 사이에 등록된 신상품의
  이벤트는 브랜드 미해석 → **그 이벤트만 스킵(warn 로그)** — 다음 리프레시부터 집계된다.
  몇 분 창의 신상품 방문자 미집계는 감수(30분 슬라이딩 지표 특성상 자기치유).

### D5. S-1 원천 교체 — 폴백은 기존 쿼리, 신선도는 하트비트로 판정

- **선택**: S-1 조회 서비스에서 ZSET을 읽되, **Redis 장애·키 부재 시
  기존 behavior_events 30분 스캔 쿼리로 폴백**한다(07의 fail-open 원칙과 동형). 기존 쿼리는 삭제하지 않는다.
- **신선도 감지 (2026-08-10 보강)**: 브로커·컨슈머 B가 죽으면 ZSET은 **에러가 아니라 조용히 낡는다** —
  키는 살아 있으니 S-1이 낡은 숫자를 계속 읽는 구멍이 생긴다. 컨슈머 B가 poll 루프마다
  **하트비트 키**(`visitors:heartbeat`, TTL 90초)를 갱신하고, S-1은 하트비트가 없으면 ZSET을 버리고
  DB 스캔 폴백을 탄다. "파이프라인 정지 = 즉시 기존 방식 복귀"가 자동으로 성립한다.
- **트레이드오프**: 폴백 경로가 살아 있어 코드가 한 겹 두꺼워진다 — 화면 무중단이 우선.

### D6. 브로커는 KRaft 단일 노드 1대 — 복제 없음을 감수

- **기준**: 데모 규모. 브로커 유실 시나리오의 피해 = 미소비 이벤트 유실인데, DB 동기 폴백(D7)과
  `client_event_id` 멱등이 하한을 지킨다. 운영 전환 시 3대 + RF3이 표준임을 명시해둔다.
- **선택**: kafka 컨테이너 1개(KRaft, ZooKeeper 없음). 로컬은 docker-compose, 운영은 아래 확정 형상.
  `/internal` 3중 방어와 동형으로 브로커 포트는 내부망 전용 — 외부 publish 금지.
- **운영 확정 (2026-08-10, 배포 합의)**:
  - 전용 EC2 **`jarvis-kafka`** (t3.small) — 앱 EC2(t3.small×4, 어제 증설)와 동거하지 않는다.
    "일을 뺐다" 논거 성립 조건이자 메모리 격리
  - 접속: **`172.31.46.48:9092` 사설 IP 전용** (`KAFKA_BOOTSTRAP_SERVERS`, deploy.yml env — PR #152).
    퍼블릭 경로 없음
  - 보안그룹: `jarvis-kafka-sg` — 9092 인바운드는 `jarvis-backend-sg-v2` **그룹 참조**만(IP 아님 —
    앱 증설 시 자동 커버). 외부 공개 없음
  - 디스크·보존: 볼륨 30GB, **retention 7일** — 시연(8/14)에서 리허설(8/12~13) 데이터까지 되감기
    데모에 쓸 수 있게 3일에서 상향. 되감기 데모 자체는 당일 이벤트로도 성립하므로 7일은 여유분
  - `restart: unless-stopped` + 브로커 EC2 StatusCheck 알람(D7 관측)

### D7. produce 실패 정책 — 동기 DB 폴백, 500은 최후 (2026-08-10 전면 개정 — 배포 리뷰 반영)

단일 브로커(D6)는 새 SPOF다. 브로커가 죽으면(컨테이너 OOM·EC2 재부팅·디스크 풀) produce가 실패하는데,
그때 E-1이 무엇을 반환할지는 별도의 결정이다.

> **연혁**: 1차 개정은 fail-fast 500이었다(계약 준수·관측성 근거). 배포 리뷰가 세 가지를 지적해 전면 개정:
> ① 경로별 5xx 알람이 현 ALB 구조(단일 대상그룹)로는 불가 — 전체 5xx에 묻힌다 ② 단일 브로커 장애가
> 시연(8/14) 중 브라우저 콘솔 에러·SDK 재전송 반복으로 가시화된다 ③ D5가 폴백을 두면서 여기만
> fail-fast인 것은 비일관. 수용하되 "조용한 드롭"으로 돌아가지 않는다 — **동기 DB 폴백**으로
> 유실을 늘리지 않으면서 가시 실패도 없앤다.

- **선택지**: (A) 500 반환 — SDK 재전송 위임 (B) **produce 실패 → 기존 적재 경로로 동기 INSERT → 202,
  그마저 실패 시 500** (C) 조용히 드롭 후 202
- **선택**: (B).
  - **성립 조건 — producer 타임아웃 확정값 (2026-08-10, 배포 리뷰 반영)**: 기본값의 `max.block.ms`는
    **60초**다 — 브로커가 죽으면 produce 호출이 요청 스레드를 60초씩 물고, 평상시 트래픽(초당 수십 건)만으로도
    1분 안에 톰캣 스레드가 고갈된다. **폴백이든 500이든 그 판정에 도달하기 전에 앱 전체가 죽는다** —
    "폭발 반경은 E-1뿐"이라는 이 문서의 주장은 아래 값이 있어야만 성립한다:
    `max.block.ms=1000` · `request.timeout.ms=1000` · `delivery.timeout.ms=2000` · `retries=1`.
    브로커 다운 시 E-1 추가 지연 상한 ≈ 1~3초(그 후 폴백), 스레드 점유는 유한하다
  - **⚠️ 500은 재전송이 아니라 유실이다 (2026-08-10 FE 조사로 확인)** — 노션 E-1은 "500이면 SDK가
    그대로 재전송한다"고 규정하지만, 실제 FE 구현은 **응답 상태를 검사하지 않고 실패를 삼킨다**
    (jarvis-frontend `src/shared/analytics/track.ts` — `flush()`가 전송 전에 큐를 비우고 빈 `catch`로
    끝난다. 주석에 *"재시도하면 중복·부하만 는다"*고 의도가 적혀 있다. 401 재전송도 없다).
    즉 **fail-fast 500을 골랐다면 브로커 장애가 곧 실데이터 유실**이었다 — 폴백이 유실을 막는
    유일한 경로임이 실증됐다. **정본은 2026-08-10 이 현실에 맞춰 개정**했다(§3-3 ②)
  - **사용자 가시 실패 없음** — 브로커가 죽어도 E-1은 202를 유지한다. 시연 리스크 0
  - **목표 3 생존** — 202는 여전히 "영속 매체에 실렸음"을 뜻한다(카프카 **또는** DB).
    (C)와의 결정적 차이 — 폴백은 유실을 만들지 않는다
  - **계약 준수** — 노션 E-1의 "저장 실패 시 500"은 **카프카·DB가 모두 실패한 경우**에만 발동한다.
    계약 문구와 구현이 §3-3대로 일치한다
  - **중복 무해** — produce가 타임아웃으로 "실패처럼 보였지만 실제 성공"이면 DB 폴백과 컨슈머 A 적재가
    겹치는데, `client_event_id` UNIQUE(D3)가 흡수한다. 폴백 경로가 안전한 이유도 결국 멱등성이다
  - **정합적 강등** — 브로커 장애 시: 적재는 DB 직행(이 항) + S-1은 하트비트 소멸로 DB 스캔 폴백(D5)
    → **시스템 전체가 도입 이전 아키텍처로 자동 복귀**하고, 브로커 복구 시 역방향도 자동이다.
    부분 장애가 반쪽 상태를 만들지 않는다
- **§1-1과의 일관성**: 비목표 "유실 방지"는 *유실 방지를 도입 사유로 주장하지 않는다*는 뜻이지
  유실 확대를 허용한다는 뜻이 아니다 — 폴백은 유실을 늘리지 않으므로 이 원칙에 정확히 부합한다.
- **관측 (1차 개정의 E-1 5xx 알람 폐기)**: ① 브로커 EC2 StatusCheck 알람(배포 소관) ②
  `visitors:heartbeat` 부재 = 파이프라인 정지 신호(D5) ③ 컨슈머 랙 지표(구현 후 노출).
  폴백 발동 시 서버 로그 warn — "조용한 유실"이 아니라 "기록되는 강등"이다.
- **트레이드오프**: 폴백 중 컨슈머 B가 해당 이벤트를 못 본다 — 같은 구간에 하트비트가 S-1을 DB로
  돌려놓으므로 지표는 정합하다. 동기 INSERT만큼 폴백 구간의 E-1 지연이 늘지만, 드문 경로다.

### D8. "캐시 30초" 대안 검토 — 빈도 감소와 작업 소멸은 다르다 (2026-08-10 신설)

가장 강한 반론은 "activeVisitors를 30초 캐시하면 되지 않나"다. 정면으로 검토한다.

- **구조 비교**:

  | | 캐시 30초 | 스트림 집계 (본 설계) |
  |---|---|---|
  | 30분 스캔 | **남는다** — 30초마다 1회 실행 | **소멸** — 조회는 ZCARD 한 번 |
  | 부하 주체 | `behavior_events`(최대 테이블) 스캔이 **결제와 같은 RDS**에서 주기 실행 | RDS 무관(Redis) |
  | 신선도 | 최대 30초 낡음 | 초 단위 |

  캐시는 **조회 횟수를 줄이고**, 스트림 집계는 **작업 자체를 없앤다**. 이것은 명세와 무관한 구조적 사실이다.
- **검증**: §5-2의 전/후 실측(30분 스캔 vs ZCARD)이 이 차이를 숫자로 만든다. 구조 논증은 측정으로 닫는다.
- **맥락**: 팀은 RDS 부하 대응(#147·#148)으로 캐시를 2종→5종으로 확장하면서도 이 지표는 실시간 성격으로
  캐시 비대상으로 남겼다(§2-2). 캐시로 가려면 그 판단을 뒤집는 결정이 먼저 필요하다.
- **정직한 인정**: 그럼에도 **캐시도 답이 된다** — 대시보드 숫자가 30초 낡아도 체감 차이는 없다.
  "캐시로는 안 된다"가 아니라, **"Kafka를 써야 한다면(§1 도전 과제) 여기가 가장 말이 되는 자리"**가
  이 설계의 정확한 주장이며, 그 이상을 주장하지 않는다(부록 A Q&A).

### D9. 컨슈머 배치 — 백엔드 앱 내 리스너, 별도 배포 단위를 만들지 않는다 (2026-08-10 신설, 배포 질의 회신)

- **선택지**: (A) Spring 앱 내 `@KafkaListener` — 4대에 컨슈머 그룹 분산 (B) `jarvis-kafka` EC2에 별도
  컨슈머 프로세스 (C) 별도 레포·별도 배포
- **기준**: "병목 계층에서 일을 뺐다" 논거의 **정확한 범위**. 이 설계가 없애는 작업은 **RDS의 30분 스캔과
  S-1 조회 경로의 집계**이지, 앱 계층의 적재가 아니다. 적재(INSERT)는 **지금도 앱 4대가 `@Async`로 하는
  일**이며, 카프카 이후에도 같은 계층이 같은 일을 한다 — 바뀌는 것은 트리거(HTTP 요청 → 토픽)다.
  새로 추가되는 앱 계층 작업은 ZADD 몇 번뿐이다. 따라서 (A)가 논거를 죽이지 않는다.
- **선택**: (A).
  - 엔티티·리포지토리·상품→브랜드 매핑을 **그대로 재사용** — (B)·(C)는 코드 중복 또는 공유 모듈 신설
  - 배포 파이프라인 무변경 — deploy.yml에 env 1줄(PR #152)이 전부
  - 컨슈머 그룹이 4대에 분산되어 컨슈머 자체는 단일 장애점이 아니다. 파티션 3 ← 인스턴스 4라 1대는
    대기(파티션 수 = 그룹 병렬 상한 — 의도된 여유)
  - (B)는 브로커와 컨슈머가 한 EC2에서 운명공동체가 되는 역설 — 브로커 장애 대비책(D5·D7)이 무의미해진다
- **파급**: 배포에서 선제로 열어둔 `jarvis-db-sg` 3306 ← kafka-sg, `jarvis-redis-sg` 6379 ← kafka-sg
  인바운드는 **당장 불필요**해진다(컨슈머가 앱 SG 안에서 돌므로 기존 허용으로 충분). 회수/유지는 배포 판단 —
  향후 컨슈머 분리(§6) 시 재사용 가능하니 남겨도 무해하다.
- **배포 리밸런싱**: 롤링 배포(max-parallel 2)마다 컨슈머 재시작으로 리밸런싱이 발생한다 — 수집 특성상
  수 초 정지는 무해. 시끄러워지면 static membership(`group.instance.id`)이 다음 손잡이다.

### 3-3. 부수 해소 — E-1 계약·구현 불일치

불일치는 **두 갈래**였고, 각각 반대 방향으로 정리됐다.

**① BE 쪽 — 구현이 정본을 따라간다(이 설계).** 구 구현은 저장 전에 202를 반환(`@Async`)해
"저장 실패 시 500"이 발동할 수 없었다(부하 테스트 §6에서 확인). 이제 **카프카·DB 폴백이 모두
실패했을 때만 500**을 내므로(D7) 계약 문구가 구현과 일치한다 — 202를 준 것은 반드시 영속됐다.

**② FE 쪽 — 정본이 현실을 따라간다(2026-08-10 노션 개정).** 정본의 "SDK가 재전송한다"는
FE에 구현돼 있지 않고, 앞으로도 그럴 계획이 없다(의도적 선택 — D7 참조). 정본을 고쳐 **현재 동작을
기술**하도록 바꾸고, 재전송을 전제로 만들어졌던 **401 정책은 🔴 미결로 남겼다** — AT 만료 구간의
이벤트가 통째로 사라지는 문제라 FE 재전송 구현이든 정책 철회든 팀 결정이 필요하다.
자료실 「🧩 API 명세와의 정합 요구사항」 2026-08-10 항목에 FE 할 일로 등재했다.

> ⚠️ 이 결정은 **정본을 구현에 맞춘 예외적 방향**이다(CLAUDE.md 계약 위계의 기본은 그 반대).
> 근거는 FE의 미구현이 사고가 아니라 명시적 설계 선택이고, 정본이 사실과 다른 채로 남으면
> 이 문서를 읽는 다른 레인이 "실패해도 재전송되니 괜찮다"고 잘못 판단하기 때문이다.

## 5. 검증 계획

1. **통합 테스트**: produce→consume→INSERT 왕복, 중복 전달 시 A(행 수 불변)·B(ZCARD 불변) 검증, 폴백 전환 검증
2. **전/후 실측** (부하 테스트와 동일 방법론): S-1 응답 시간(30분 스캔 vs ZCARD), 부하 중 E-1 202 지연 분포
3. **데모 시나리오**: 상품 클릭 → 수 초 내 판매자 대시보드 방문자 증가 / 오프셋 되감기 재처리 시연

## 6. 향후 확장 — 컨슈머 그룹 추가만으로

실시간 트렌딩 지표 → 판매자 이상 알림(전달 채널이 생기면) → I-6·I-13에 실시간 값 제공(AI 분석 에이전트가
"지금" 질문에 답하게) → I-17 CDC 전환(벡터DB 소비자가 늘면). 어느 것도 기존 컨슈머·프로듀서 수정 없이
그룹 추가로 성립한다 — 이 확장 형태가 Kafka를 선택한 구조적 이유다.

## 부록 A. 발표 플로우 (7장)

1. **동기** — "도전 과제로 Kafka가 주어졌다. 도입을 위한 도입은 하기 싫었다. 그래서 '어디에 넣으면 안 되는가'부터 판정했다"
2. **판정 기준** — §2-1의 4문
3. **기각 목록** — §2-2 표 (후보당 한 줄) ← 차별화 슬라이드
4. **선정** — 시점 근거(지표는 7/21 대시보드 확정 때 정의 — Kafka 검토보다 3주 먼저 존재한 요구) +
   구조 근거(D8 — 캐시는 스캔 빈도를 줄이고, 스트림 집계는 스캔을 없앤다) + 전/후 실측(§5).
   ⚠️ "명세에 실시간이라 적혀 있다"는 근거로 쓰지 않는다 — §2-2의 순환논증 금지와 동일 기준
5. **아키텍처** — §0 그림 + 멱등 설계(D3, ZADD 자연 멱등)
6. **데모** — 클릭→숫자 상승, (여유 시) 오프셋 되감기
7. **한계와 확장** — 단일 브로커·at-least-once 인지(D6·D3) → §6

**Q&A 대비 (슬라이드 미포함)** — 같은 톤의 카드 3장: **먼저 인정하고, 한정된 주장으로 좁힌다.**

1. "이 규모에 오버엔지니어링 아닌가?"
   → "맞다, 부하 때문이 아니다. 부하 테스트로 유실·부하 근거가 없음을 확인했고(유실 0건, 이벤트 경로는
   전체 HTTP 요청 수의 1.2%), 그래서 도입 사유를 실시간 지표 구현으로 한정했다."
2. "캐시 30초로도 되지 않나?"
   → "맞다, 개선된다. 다만 캐시는 30분 스캔의 빈도를 줄이고, 스트림 집계는 스캔 자체를 없앤다 —
   그 차이를 전/후 실측으로 제시한다(D8). Kafka를 써야 한다면 여기가 가장 말이 되는 자리라고 판단했다."
3. "브로커 하나 죽으면 수집이 멈추지 않나?"
   → "맞다, 단일 브로커는 SPOF다. 그래서 produce 실패 시 기존 DB 적재로 동기 폴백해 202를 유지하고,
   같은 순간 하트비트 소멸로 S-1도 DB 조회로 돌아간다 — 브로커가 죽으면 시스템 전체가 도입 이전
   아키텍처로 정합하게 강등됐다가 복구 시 자동 복귀한다(D7·D5). 사용자 가시 영향과 유실 모두 0이다.
   전제는 producer 타임아웃 확정값이다 — 기본 60초 블로킹을 방치하면 스레드 고갈로 앱 전체가 죽는다(D7)."
4. "팬아웃이면 SNS+SQS로도 되지 않나?"
   → "맞다, 팬아웃만이면 SNS+SQS 조합으로도 된다. 못 하는 것은 **되감기**다 — SQS는 꺼내서 확인(ack)하면
   메시지가 사라지므로, 집계 로직을 고친 뒤 과거 이벤트를 다시 읽는 재처리(§5 데모)가 구조적으로 불가능하다.
   보존된 로그에서 오프셋을 되감는 능력이 이 파이프라인의 요구사항이라 Kafka를 골랐다."
