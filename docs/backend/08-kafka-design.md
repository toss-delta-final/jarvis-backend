## 0. 요약

Kafka에 태우는 것은 **행동 이벤트 수집 경로(E-1) 하나**다.
검토했으나 **태우지 않기로 한 것이 더 많고**, 그 판단 근거가 이 문서의 절반이다.

```
FE ──HTTP──▶ E-1 엔드포인트 (검증·신원주입·문맥보강 — 기존 그대로)
                 │  produce 성공 → 202 / 실패 → 500 (SDK 재전송)
                 ▼
        Kafka topic: behavior-events  (파티션 3, key = sessionKey)
                 │
    ┌────────────┴──────────────┐
    ▼                           ▼
컨슈머 그룹 A: persister      컨슈머 그룹 B: visitor-tracker
배치 INSERT → behavior_events   상품→브랜드 해석 후
(멱등: client_event_id UNIQUE)  Redis ZSET visitors:{brandId} 갱신
                                → S-1 activeVisitors의 새 원천
```

| 항목 | 결정 | 근거 절 |
|---|---|---|
| 도입 위치 | E-1 수집 경로 + S-1 `activeVisitors` 원천 교체 | §2 |
| 도입하지 않는 곳 | 주문·매출·aiAttribution·I-17·캐시 무효화 | §2-2 |
| 전달 보장 | at-least-once + 컨슈머 멱등 | D3 |
| 브로커 | KRaft 단일 브로커 1대 (compose) — 데모 규모 감수 | D6 |
| 장애 시 | produce 실패 = 500(계약대로), 컨슈머 장애 = 폴백/재개 | §4 |

## 1. 배경 — 왜 지금, 왜 이 자리인가

- MVP(2026-07-27 종료)는 Kafka 없이 완성했다. 동기 HTTP + DB 집계로 충분한 규모였고, 이는 의도된 선택이다.
- 도전 과제 "Kafka 기반 실시간 데이터 스트림 처리"를 수행하되, **도입을 위한 도입을 피하기 위해
  전 시스템을 후보로 놓고 적합성 판정을 먼저 수행**했다(§2). 탈락 근거를 남기는 것까지가 이 설계의 범위다.
- 부하 테스트(2026-08-08, `부하테스트-병목분석-20260808.md`)로 **"부하·유실 때문에 Kafka가 필요하다"는
  가설은 기각**됐다 — 커넥션 풀 포화 상태에서도 이벤트 유실 0건, 이벤트 경로는 전체 부하의 1.2%.
  따라서 이 설계의 도입 사유에 부하·유실은 **없다**(§1-1 비목표).

### 1-1. 목표 / 비목표

**목표**
1. E-1 수집 경로를 스트림 파이프라인으로 전환 — 같은 이벤트를 저장계(A)와 실시간계(B)가 독립 소비
2. S-1 `today.activeVisitors`(명세: "실시간, 캐시 미적용")를 매 조회 30분 스캔 쿼리 → 라이브 집계로 교체
3. E-1 202 응답의 의미를 "인메모리 큐 수신"에서 "로그 영속"으로 승격 — 노션 E-1의
   "저장 실패 시 500 → SDK 재전송" 문구를 구현이 실제로 이행하게 만든다(§3-3)

**비목표 (명시적으로 아님)**
- ~~유실 방지·부하 흡수~~ — 부하 테스트로 근거 없음이 실측됨. 이 사유를 대외적으로 주장하지 않는다
- ~~주문·매출 스트림화~~ — 돈은 근사 불가, 정본은 `order_item` 집계(02 D32·I-13 개정 원칙)
- ~~I-17 CDC 전환~~ — §2-2
- 다중 브로커·exactly-once — 데모 규모 밖(D6)

## 2. 적합성 판정 — 어디에 넣고, 어디에 안 넣는가

### 2-1. 판정 기준 4문

1. 한 사건을 **서로 다른 관심사의 소비자** 여럿이 각자 소비하는가 (팬아웃)
2. **실시간성** 요구가 명세에 있는가 ("물어볼 때 계산"이면 탈락)
3. **소급 정정 없는 현재-순간 값**인가 (취소 소급·정책 재계산이 있으면 스트림 물질화 부적합)
4. **팀 간 계약 변경 없이** 가능한가 (노션 명세·타 repo 무변경)

### 2-2. 후보별 판정

| 후보 | 판정 | 근거 |
|---|---|---|
| **E-1 + S-1 activeVisitors** | ✅ **채택** | 4문 전부 통과 — 아래 |
| I-17 상품→벡터DB 동기화 | ❌ | CDC의 교과서 자리지만 소비자 1명·분 단위 지연 허용·AI팀 계약 개정 필요. 소비자가 늘면 재평가 1순위 |
| 주문 이벤트 발행 | ❌ | 후속 소비자(알림·정산)가 기획에 없음 — Kafka를 위해 기능을 발명하게 됨 |
| 매출·주문 지표 스트림화 | ❌ | 돈은 근사 불가. 이벤트는 신호, 정본은 DB라는 기존 결정(I-13 purchaseComplete 개정)과 충돌 |
| S-1 aiAttribution | ❌ | 취소 **소급** 반영·귀속 창 재계산·policyVersion 재평가가 요구사항 — "집계 시점 사후 판정"(S-1 명세)이 정답. 스트림 물질화하면 소급이 불가능해짐 |
| 캐시 무효화 (Redis·FE) | ❌ | 늦게 도착한 무효화는 가치 0 — 보존·재생이 전부 낭비. 07 §5의 기존 기각 유지 |
| 판매자 분석(I-6~I-16) 실시간화 | ❌ | 전부 "질의 시점 계산" 요구 — 실시간 감지·알림은 기획에 없음. 채널이 생기면 컨슈머 그룹 추가로 확장(§6) |

**채택 근거 상세** — `activeVisitors`가 유일하게 4문을 전부 통과한다:
- 원천이 `behavior_events`(= 파이프라인에 흐르는 그 데이터)다
- S-1 명세가 **"성격이 실시간이라 캐시 미적용"**이라고 명시한, 이 시스템의 유일한 실시간 지표다 — 기능 발명이 아니라 명세에 있던 실시간을 실시간답게 만드는 것
- 30분 지나면 사라지는 현재-순간 값이라 소급·정정 개념이 없다
- DISTINCT 집계라 **집합 연산으로 자연 멱등** — at-least-once 중복 전달이 숫자를 틀리게 하지 못한다(D3)
- 응답 계약·화면 무변경 — 숫자의 원천만 바뀐다

## 3. 결정 로그

### D1. 토픽은 하나, 키는 sessionKey

- **선택지**: (A) 토픽 1개 `behavior-events` (B) 이벤트 타입별 토픽 분리
- **기준**: 소비자 2개(A·B)가 모두 전 타입을 읽는다. 타입별 분리는 컨슈머 구독만 복잡하게 한다.
- **선택**: (A). 파티션 3 (데모 규모 + 컨슈머 병렬도 여유). 키 = `sessionKey` —
  같은 세션의 이벤트 순서가 보존되고(파티션 내 순서), 세션 수가 많아 핫 파티션이 없다.
  키를 `brandId`로 하면 대형 브랜드 쏠림, 키 없음이면 세션 순서 상실 — 둘 다 기각.
- **트레이드오프**: 파티션 증설 시 같은 세션의 신·구 이벤트가 다른 파티션에 갈라진다(증설은 신중히).

### D2. 프로듀서 — E-1 엔드포인트는 그대로, 적재만 교체

- **선택지**: (A) FE가 직접 브로커/REST Proxy로 발행 (B) E-1 엔드포인트 유지, `@Async` INSERT를 produce로 교체
- **기준**: E-1의 서버 로직(JWT/쿠키 신원 주입, 타입 화이트리스트, 추천 문맥 검증 ③.5, 게스트 쿠키 발급)은
  HTTP 요청 문맥을 요구한다. 브로커 인터넷 노출은 인증·어뷰징 방어를 재발명하게 한다.
- **선택**: (B). 검증·보강 **후**의 완성된 이벤트를 produce한다. 서버 적재 3종
  (`recommendation_generated`·`add_to_cart`·`remove_from_cart`)도 같은 프로듀서를 경유해 적재 경로를 단일화한다.
- **트레이드오프**: produce 동기 대기(acks)만큼 202가 미세하게 늦어진다 — 로컬 브로커라 ms 단위, 감수.

### D3. 전달 보장 — at-least-once + 컨슈머별 멱등

- **기준**: exactly-once는 외부 세계(DB·Redis)를 건드리는 순간 성립하지 않는다. 중복을 전제로 설계한다.
- **선택**:
  - **컨슈머 A**: `client_event_id` UNIQUE(02 D35)가 이미 있다 — 재전달·재처리 모두 DB가 흡수. 기존 배치 INSERT 로직 이식.
  - **컨슈머 B**: `ZADD`는 집합 연산이라 같은 (sessionKey, 시각) 재적용이 결과를 바꾸지 않는다 — 구조적 멱등.
- **트레이드오프**: 없음에 가깝다. 이 자리를 고른 이유 자체가 멱등이 공짜인 자리라서다(§2-2).

### D4. 컨슈머 B — visitor-tracker의 자료구조

- **선택지**: (A) 브랜드별 ZSET `visitors:{brandId}`, member=sessionKey, score=이벤트 시각 (B) HyperLogLog 분 버킷
- **기준**: S-1 정의는 "최근 30분 자사 상품 관련 이벤트의 DISTINCT session_key". 정확한 값 + 슬라이딩 윈도우 + 구현 단순성.
- **선택**: (A). 갱신 = `ZADD`, 조회 = `ZREMRANGEBYSCORE`(30분 밖 제거) + `ZCARD`.
  브랜드 귀속은 컨슈머가 `product_id → brand_id`를 해석(로컬 캐시 가능한 매핑, 스코프 규칙은 S-1과 동일).
  TTL은 키 전체에 40분 — 이벤트가 끊긴 브랜드의 키를 자동 정리.
- **트레이드오프**: 세션 수 × 브랜드 수만큼 메모리를 쓴다 — 동시 1만 세션 기준 수 MB, 07의 예산(§4-4 참조) 안.
  (B) HLL은 메모리는 적지만 근사치라 "정확한 셋"이라는 채택 근거(§2-2)를 스스로 깬다 — 기각.

### D5. S-1 원천 교체 — 폴백은 기존 쿼리

- **선택**: `HomeRecommendationService`류가 아니라 S-1 조회 서비스에서 ZSET을 읽되, **Redis 장애·키 부재 시
  기존 behavior_events 30분 스캔 쿼리로 폴백**한다(07의 fail-open 원칙과 동형). 기존 쿼리는 삭제하지 않는다.
- **트레이드오프**: 폴백 경로가 살아 있어 코드가 한 겹 두꺼워진다 — 화면 무중단이 우선.

### D6. 브로커는 KRaft 단일 노드 1대 — 복제 없음을 감수

- **기준**: 데모 규모. 브로커 유실 시나리오의 피해 = 미소비 이벤트 유실인데, E-1 SDK 재전송(§3-3)과
  `client_event_id` 멱등이 하한을 지킨다. 운영 전환 시 3대 + RF3이 표준임을 명시해둔다.
- **선택**: docker-compose에 kafka 컨테이너 1개(KRaft, ZooKeeper 없음). `/internal` 3중 방어와 동형으로
  브로커 포트는 내부망 전용 — 외부 publish 금지.

### 3-3. 부수 해소 — E-1 계약·구현 불일치

노션 E-1 정본은 실패 응답에 **"500 `INTERNAL_ERROR` — 배치 INSERT 자체가 실패. SDK는 그대로 재전송"**을
규정하지만, 현 구현은 저장 전에 202를 반환(`@Async`)해 이 재전송 경로가 작동하지 않는다
(부하 테스트 §6에서 확인된 드리프트). 이 설계에서는 **produce 실패 시 500**을 반환하므로
계약 문구가 구현과 다시 일치한다. 노션 변경은 불필요 — 구현이 정본을 따라가는 방향이다.

## 4. 장애 시나리오

| 상황 | 동작 | 피해 |
|---|---|---|
| 브로커 다운 | E-1이 500 → SDK 재전송(계약대로) | 수집 지연. 유실 없음(`client_event_id` 멱등) |
| 컨슈머 A 다운 | 이벤트는 토픽에 보존, 복구 후 오프셋부터 재개 | 적재 지연만 |
| 컨슈머 B 다운 / Redis 장애 | S-1이 기존 스캔 쿼리로 폴백(D5) | 화면 무중단, 숫자 신선도만 하락 |
| 재처리 필요(로직 수정 등) | 오프셋 리셋 후 재소비 — A는 UNIQUE, B는 집합이 중복 흡수 | 없음 |
| 컨슈머 랙 누적 | 랙 지표 모니터링(운영 항목) — 임계 초과 시 경고 | 지표 지연 |

## 5. 검증 계획

1. **통합 테스트**: produce→consume→INSERT 왕복, 중복 전달 시 A(행 수 불변)·B(ZCARD 불변) 검증, 폴백 전환 검증
2. **전/후 실측** (부하 테스트와 동일 방법론): S-1 응답 시간(30분 스캔 vs ZCARD), 부하 중 E-1 202 지연 분포
3. **데모 시나리오**: 상품 클릭 → 수 초 내 판매자 대시보드 방문자 증가 / 오프셋 되감기 재처리 시연

## 6. 향후 확장 — 컨슈머 그룹 추가만으로

실시간 트렌딩 지표 → 판매자 이상 알림(전달 채널이 생기면) → I-6·I-13에 실시간 값 제공(AI 분석 에이전트가
"지금" 질문에 답하게) → I-17 CDC 전환(벡터DB 소비자가 늘면). 어느 것도 기존 컨슈머·프로듀서 수정 없이
그룹 추가로 성립한다 — 이 확장 형태가 Kafka를 선택한 구조적 이유다.

## 부록 A. 발표 플로우 (7장)

1. **동기** — "도전 과제로 Kafka가 주어졌다. 도입을 위한 도입은 하기 싫었다. 그래서 '어디에 넣으면 안 되는가'부터 판정했다"
2. **판정 기준** — §2-1의 4문
3. **기각 목록** — §2-2 표 (후보당 한 줄) ← 차별화 슬라이드
4. **선정** — S-1 명세 원문 인용("실시간, 캐시 미적용") + "명세에 있던 실시간을 실시간답게"
